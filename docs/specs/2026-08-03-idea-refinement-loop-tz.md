# ТЗ: Kaidzen — самоулучшающийся Idea Refinement Loop

Двухуровневая система:
- **Уровень 1 (внутренний луп):** шлифует идею фактами из веб-поиска.
- **Уровень 2 (мета-луп):** эволюционирует конфиги и промпты Уровня 1, прогоняя его на бенчмарк-идеях и сравнивая результаты.

**Дата:** 2026-08-03
**Статус:** черновик на утверждение
**Стек:** Python 3.12+, Claude API (Anthropic SDK), server-side web search tool

---

## 1. Цель и границы

**Уровень 1.** Вход: сырая идея (1–3 абзаца, markdown). Выход: отшлифованная идея + таблица допущений с вердиктами и источниками + оценки по рубрике + история эволюции версий + next steps.

**Уровень 2.** Вход: бенчмарк из 6–10 реальных идей пользователя + стартовый «кандидат» (конфиг + промпты). Выход: улучшенный кандидат-чемпион, доказуемо дающий лучшие отчёты на бенчмарке, + линия эволюции кандидатов.

**Ключевое требование обоих уровней:** улучшение *измеримо*.
- Уровень 1: реестр допущений (каждая итерация закрывает допущения фактами) + Judge с рубрикой.
- Уровень 2: слепое попарное сравнение отчётов Meta-Judge + объективные метрики + чекпоинт человека.

**Не входит в v1:** векторная база с книгами, Telegram-бот, web UI, оптимизация архитектуры лупа (порядок шагов и состав ролей фиксированы — мета-луп меняет только конфиг и промпты).

## 2. Уровень 1: внутренний луп

Оркестратор (чистый Python, без фреймворков) гоняет цикл из 4 ролей. Каждая роль — отдельный вызов Claude API со своим системным промптом.

```
idea.md
  │
  ▼
[Analyzer]  — один раз
  │  компоненты идеи + реестр допущений
  ▼
┌─────────────── цикл (макс. N итераций) ───────────────┐
│  [Researcher] — 2–3 самых рискованных допущения        │
│      → веб-поиск → факты со статусами и источниками    │
│  [Refiner] — версия + факты + критика прошлой          │
│      итерации → новая версия + changelog               │
│  [Judge] — оценка по рубрике, сравнение с прошлой      │
│      → continue / rollback-сигнал                      │
└────────────────────────────────────────────────────────┘
  │
  ▼
[Reporter] — report.md (сборка кодом из state; LLM только
             для executive summary)
```

### 2.1 Роли: контракты

Все роли получают и возвращают JSON (structured output через tool-use со schema). Роли не видят внутренностей друг друга — только определённые ниже поля state.

#### Analyzer (один раз)
- **Вход:** текст идеи + конфиг кандидата.
- **Выход:**
  ```json
  {
    "problem": "...",
    "audience": "...",
    "mechanism": "...",
    "assumptions": [
      { "id": "A1", "text": "...", "criticality": "high|medium|low", "status": "unverified" }
    ],
    "unknowns": ["..."]
  }
  ```
- **Параметры:** temperature 0.3.

#### Researcher
- **Вход:** текущая версия идеи + 2–3 допущения с наивысшей criticality среди status=unverified.
- **Инструменты:** web_search (server-side tool), max_uses 5–8 на вызов.
- **Выход по каждому допущению:**
  ```json
  {
    "assumption_id": "A1",
    "verdict": "confirmed|refuted|partial|untestable",
    "facts": [ { "claim": "...", "source_url": "...", "source_title": "...", "date": "..." } ],
    "notes": "..."
  }
  ```
- **Правила:** каждый факт обязан иметь source_url (URL приходит из результатов web_search tool, не генерируется моделью). `untestable` = уходит в next steps, больше не выбирается.
- **Параметры:** temperature 0.2.

#### Refiner
- **Вход:** текущая версия + находки Researcher + критика Judge с прошлой итерации.
- **Выход:**
  ```json
  {
    "idea_text": "...",
    "changelog": [ { "change": "...", "reason": "...", "grounded_in": ["A1"] } ]
  }
  ```
- **Правила:** каждый пункт changelog обязан ссылаться на закрытое допущение (`grounded_in`) либо на пункт критики Judge. Правки «для красоты» запрещены промптом — защита от полировки в вакууме.
- **Параметры:** temperature 0.7.

#### Judge
- **Вход:** новая версия + предыдущая версия + реестр допущений + рубрика кандидата. **Changelog Refiner'а НЕ передаётся** — иначе Judge оценивает нарратив, а не результат.
- **Выход:**
  ```json
  {
    "scores": { "<ось>": 0 },
    "total": 0,
    "delta_vs_previous": 0,
    "critique": ["..."],
    "verdict": "continue|rollback"
  }
  ```
- **Правила:** rollback если total упал больше чем на 1.0. Решение об остановке — за оркестратором, не за Judge.
- **Параметры:** temperature 0.1.

### 2.2 Критерии остановки (оркестратор)

Стоп при **любом** из:
1. **Плато:** два раза подряд прирост total < `plateau_threshold` (default +0.5).
2. **Лимит:** `max_iterations` (default 6).
3. **Допущения исчерпаны:** все high-допущения confirmed / refuted / untestable.

Rollback: версия помечается `rolled_back`, продолжаем от предыдущей. Два rollback подряд = стоп. Причина остановки — в state и в отчёт.

### 2.3 Модели

| Роль | Модель (default) |
|---|---|
| Analyzer, Researcher, Judge | claude-sonnet-5 |
| Refiner | claude-sonnet-5 (opus — опция конфига) |

Имена моделей — в конфиге, не в коде.

## 3. Кандидат: единица эволюции

**Кандидат** = версионированная директория: конфиг + полный набор промптов. Именно кандидатов мутирует и сравнивает мета-луп.

```
candidates/
├── gen000-baseline/
│   ├── config.yaml
│   ├── prompts/
│   │   ├── analyzer.md
│   │   ├── researcher.md
│   │   ├── refiner.md
│   │   └── judge.md
│   └── meta.json        # родитель, поколение, статус (champion/rejected/pending), результаты eval
├── gen001-a/
└── ...
```

### config.yaml

```yaml
domain: "универсальный"
rubric:                      # ровно 5 осей, 0–10; groundedness обязательна
  novelty: "Новизна: отличие от существующих решений"
  feasibility: "Реализуемость с разумными ресурсами"
  groundedness: "Доля допущений, закрытых фактами"
  potential: "Потенциал: ценность при успехе"
  clarity: "Ясность формулировки"
researcher_focus: "..."
analyzer_hints: "..."
loop:
  max_iterations: 6
  plateau_threshold: 0.5
  assumptions_per_iteration: 3
models: { analyzer: claude-sonnet-5, researcher: claude-sonnet-5, refiner: claude-sonnet-5, judge: claude-sonnet-5 }
```

Кандидаты иммутабельны: мутация = новая директория с новым id и ссылкой на родителя в meta.json. Ничего не перезаписывается.

### 3.1 Стартовые доменные наборы

В v1 поставляются три рукописных кандидата (домен = отдельный кандидат, код общий):

| Кандидат | Домен | Особенности рубрики и фокуса Researcher |
|---|---|---|
| `gen000-generic` | универсальный | нейтральные оси (§3, config.yaml) |
| `gen000-business` | бизнес-идеи | оси: рынок, конкуренты, монетизация, реализуемость, groundedness; Researcher ищет размер рынка, аналоги, ценообразование |
| `gen000-games` | компьютерные игры | оси: механика/новизна геймплея, аудитория жанра, сложность разработки, потенциал, groundedness; Researcher ищет аналоги в Steam, отзывы, продажи жанра |

У каждого домена своя независимая линия эволюции и свой champion: `candidates/CHAMPION-<domain>`. `run --domain business` берёт champion'а домена; `evolve --domain games --benchmark benchmark/games/` эволюционирует только игровой набор. Бенчмарк-идеи раскладываются по доменным папкам `benchmark/<domain>/ideas/`.

## 4. Уровень 2: мета-луп

Одно поколение:

```
champion (текущий лучший кандидат)
  │
  ▼
[Diagnostician] — читает eval-результаты champion'а на бенчмарке:
  │   где слабо (какие оси, какие идеи, сколько допущений
  │   не закрыто, где Researcher промахнулся)
  │   → диагноз: 2–3 гипотезы улучшения
  ▼
[Mutator] — по диагнозу генерирует 2 кандидатов-челленджеров
  │   (правки config.yaml и/или промптов; каждая правка —
  │   с обоснованием, привязанным к диагнозу)
  ▼
[Eval] — каждый челленджер прогоняется внутренним лупом
  │   на train-части бенчмарка (детерминированные настройки:
  │   temperature ролей как в кандидате, max_iterations
  │   урезан до 4 для экономии)
  ▼
[Meta-Judge] — слепое попарное сравнение: report(champion)
  │   vs report(challenger) по каждой идее, две прогонки
  │   с перестановкой позиций (A/B и B/A). Плюс объективные
  │   метрики (§4.2)
  ▼
[Gate] — челленджер становится новым champion, только если:
  │   1) выигрывает попарку на >55% сравнений
  │   2) не регрессирует ни одну объективную метрику >10%
  ▼
[Checkpoint] — каждые K поколений (default 3) и перед финальной
      промоцией: пауза, человек глазами сравнивает отчёты
      champion vs предыдущий champion и апрувит/откатывает
```

### 4.1 Бенчмарк

`benchmark/ideas/*.md` — 6–10 реальных идей пользователя. Разбивка:
- **train** (~70%): на них Diagnostician ставит диагноз и Meta-Judge сравнивает в каждом поколении.
- **holdout** (~30%): не участвуют в цикле мутаций; прогоняются только на чекпоинтах. Если champion лучше на train, но не лучше на holdout — переобучение под бенчмарк, откат.

### 4.2 Объективные метрики (анти-Гудхарт)

Считаются кодом из state, не LLM-ом:

| Метрика | Что ловит |
|---|---|
| `assumptions_closed_rate` — доля high-допущений, доведённых до вердикта | суть работы системы |
| `facts_with_valid_sources` — доля фактов с URL из web_search-результатов | галлюцинации источников |
| `iterations_to_stop` и причина остановки | вырождение лупа (стоп по лимиту = плохо) |
| `rollback_count` | нестабильность |
| `cost_tokens`, `cost_searches` | конфиг не должен «улучшаться» за счёт 3× цены |

Gate по метрикам жёсткий: красивый отчёт при упавшем `assumptions_closed_rate` = отказ кандидату.

### 4.3 Роли мета-уровня

| Роль | Модель | temperature | Заметки |
|---|---|---|---|
| Diagnostician | claude-opus-5 | 0.3 | видит state всех прогонов champion'а, отчёты, метрики |
| Mutator | claude-opus-5 | 0.8 | выход — diff-описание правок + новые файлы кандидата; валидация схемы конфига обязательна |
| Meta-Judge | claude-sonnet-5 | 0.0 | видит ТОЛЬКО два отчёта (слепо, без имён кандидатов); не видит диагноз, мутации, метрики |

Разделение зрения принципиально: Meta-Judge, знающий «что чинили», оценивает намерение, а не результат.

### 4.4 Критерии остановки мета-лупа

1. `max_generations` (default 5).
2. Два поколения подряд ни один челленджер не прошёл Gate — плато.
3. Бюджет: `max_total_cost_tokens` на весь evolve-прогон (default задаётся в конфиге мета-лупа; при превышении — стоп с сохранением state).
4. Человек на чекпоинте сказал стоп.

### 4.5 Управление мета-лупом (вкл/выкл)

Мета-луп **никогда не запускается сам**. Два уровня полностью развязаны:

- `run idea.md` — только внутренний луп; берёт текущего champion'а (симлинк/запись `candidates/CHAMPION`) и шлифует идею. Мета-луп не трогается.
- `evolve` — только по явной команде, работает заданное число поколений и останавливается. Никаких фоновых процессов, демонов, кронов.

Остановка посреди evolve-прогона:
- **Ctrl+C** — безопасен в любой момент: state пишется атомарно после каждого шага, продолжение через `evolve-resume`.
- **`kaidzen evolve-stop evolve/<id>/`** — мягкая остановка: ставит флаг в state, оркестратор дозавершает текущее поколение (чтобы не бросать оплаченные eval-прогоны) и выходит. Продолжить можно позже через `evolve-resume`.
- Каждый чекпоинт — естественная точка паузы: evolve стоит и ждёт `--approve/--reject`, можно вернуться через неделю.

Улучшенные кандидаты применяются к работе только через смену `CHAMPION` — она происходит на Gate внутри evolve. Выключенный мета-луп = система работает на последнем утверждённом champion'е сколь угодно долго.

### 4.6 Стоимость (оценка)

Одно поколение ≈ 2 челленджера × 5 train-идей × полный внутренний луп (~15–25 вызовов API + до 20 web-поисков каждый) + попарки Meta-Judge. Порядок: **~200–350 вызовов API на поколение**. Поэтому: max_iterations=4 на eval-прогонах, sonnet везде кроме Diagnostician/Mutator, кэш прогонов champion'а (не перегонять его на тех же идеях повторно — результаты берутся из meta.json).

## 5. State

### Уровень 1 — прогон идеи
`runs/<timestamp>-<slug>/state.json`. Атомарная запись (tmp + rename) после каждого шага роли; прерванный прогон продолжается через `resume`.

```json
{
  "run_id": "...", "candidate_id": "gen000-baseline",
  "config": { "...": "снапшот" },
  "original_idea": "...",
  "analysis": { "...": "выход Analyzer" },
  "assumptions": [ { "id": "A1", "text": "...", "criticality": "high", "status": "...", "facts": [] } ],
  "versions": [ { "n": 1, "idea_text": "...", "changelog": [], "judge": {}, "rolled_back": false } ],
  "iteration": 3, "rollbacks": 0, "stop_reason": null,
  "last_completed_step": "judge",
  "api_usage": { "input_tokens": 0, "output_tokens": 0, "web_searches": 0 }
}
```

Versions только дописываются, не перезаписываются.

### Уровень 2 — evolve-прогон
`evolve/<timestamp>/state.json`: текущий champion, поколение, список кандидатов со статусами и результатами eval (попарки, метрики, ссылки на runs), история Gate-решений, чекпоинты человека, суммарный расход. Тоже атомарно, тоже resume.

## 6. CLI

```
# Уровень 1
python -m kaidzen run idea.md [--candidate candidates/gen000-baseline] [--max-iter 6]
python -m kaidzen resume runs/<run_id>/
python -m kaidzen report runs/<run_id>/

# Уровень 2
python -m kaidzen evolve [--generations 5] [--benchmark benchmark/]
python -m kaidzen evolve-resume evolve/<evolve_id>/
python -m kaidzen evolve-stop evolve/<evolve_id>/    # мягкая остановка после текущего поколения
python -m kaidzen checkpoint evolve/<evolve_id>/   # показать сравнение, апрув/откат
```

Прогресс в stdout: итерации, вердикты, оценки, дельты; в evolve — поколения, победы в попарках, метрики, расход. `ANTHROPIC_API_KEY` только из env; отсутствие = понятная ошибка на старте.

Чекпоинт: `evolve` останавливается, печатает путь к сравнительной сводке (`evolve/<id>/checkpoints/gen003.md`: отчёты champion vs предыдущий на holdout-идеях + метрики), ждёт `checkpoint --approve|--reject`.

## 7. Выходные артефакты

### report.md (Уровень 1)
1. Executive summary (3–5 предложений — единственная LLM-генерация Reporter'а).
2. Финальная версия идеи.
3. Таблица оценок по рубрике с динамикой v1→vN.
4. Таблица допущений: criticality, вердикт, факты со ссылками.
5. Эволюция версий: total-оценка + 1–2 ключевых изменения на версию.
6. Next steps: допущения untestable.

### evolve-отчёт (Уровень 2)
`evolve/<id>/summary.md`: линия эволюции кандидатов (кто от кого, что менялось, почему), динамика метрик по поколениям, итоговый champion с diff против baseline, решения человека на чекпоинтах.

## 8. Обработка ошибок

- **API-ошибки:** retry SDK + 3 повтора шага; после исчерпания state сохранён, «продолжи через resume/evolve-resume».
- **Невалидный выход роли:** structured output + 1 повтор с текстом ошибки валидации, потом фейл шага.
- **Mutator сломал конфиг:** валидация pydantic-схемой; невалидный кандидат отбрасывается, Mutator перевызывается 1 раз; двойной фейл = поколение идёт с одним челленджером.
- **Web search пусто:** допущение → untestable, луп продолжается.
- **Упал eval-прогон одной идеи:** идея помечается failed для этого кандидата, попарка по ней пропускается; кандидат с ≥2 failed = отклонён (нестабильность).
- **Бюджет:** превышение `max_total_cost_tokens` = мягкий стоп с сохранением state.

## 10. Тестирование

TDD, покрытие 80%+. LLM-вызовы мокаются фикстурами.

- **Unit:** критерии остановки обоих лупов; выбор допущений; метрики из фикстурного state; Gate (победа в попарке + непроседание метрик, все ветки); валидация кандидата (битый YAML, лишние оси рубрики, отсутствие groundedness); атомарность записи; разбивка train/holdout детерминирована.
- **Integration (моки):** полный внутренний цикл 3 итерации; resume обоих уровней; rollback-сценарий; поколение мета-лупа целиком: диагноз → 2 мутации → eval → попарки → Gate → смена champion; сценарий «переобучение»: лучше на train, хуже на holdout → откат; сборка обоих отчётов.
- **E2E smoke (реальный API, вручную):** `run` на одной идее с max_iterations=2; `evolve` на 2 идеях × 1 поколение.

Ключевые кейсы: `два поколения без промоций → стоп`; `Meta-Judge даёт разные вердикты при перестановке A/B → сравнение считается ничьёй`; `кандидат дешевле, но assumptions_closed_rate −15% → отказ`.

## 11. Этапы реализации

1. **Каркас:** state, candidate, config-схемы + тесты. → verify: unit зелёные.
2. **LLM-обёртка:** structured output, retry, usage. → verify: unit на ретраи/валидацию.
3. **Роли Уровня 1 + промпты baseline-кандидата.** → verify: контрактные тесты ролей.
4. **Оркестратор Уровня 1:** цикл, стоп-критерии, resume, report. → verify: integration полного цикла.
5. **E2E smoke Уровня 1** на реальной идее, тюнинг baseline-промптов руками. → verify: осмысленный отчёт, допущения закрываются фактами. *Внутренний луп должен стабильно работать до старта мета-лупа — иначе мета-луп оптимизирует шум.*
6. **Метрики + Gate.** → verify: unit на фикстурах.
7. **Мета-роли:** Diagnostician, Mutator, Meta-Judge. → verify: контрактные тесты, слепота Meta-Judge проверена тестом (в промпт не попадают id кандидатов и диагноз).
8. **evolve-оркестратор:** поколения, чекпоинты, resume, summary. → verify: integration поколения на моках.
9. **E2E smoke evolve:** 2 идеи × 1 поколение, реальный API. → verify: линия эволюции читаема, Gate срабатывает осмысленно.

Пользователь параллельно готовит 6–10 бенчмарк-идей (нужны к этапу 9).

## 12. Риски

| Риск | Защита |
|---|---|
| Гудхарт: отчёты красивее, идеи не лучше | Слепые попарки с перестановкой позиций; объективные метрики кодом; holdout-идеи; чекпоинты человека |
| Полировка в вакууме (Уровень 1) | changelog с обязательным grounded_in; ось groundedness; Judge не видит changelog |
| Judge/Meta-Judge-инфляция | попарное сравнение вместо абсолютных оценок; temperature 0–0.1; перестановка A/B |
| Переобучение под бенчмарк | holdout-разбивка, проверка на чекпоинтах |
| Мета-луп оптимизирует шум (нестабильный Уровень 1) | этап 5: внутренний луп доводится и проверяется до старта мета-работ |
| Стоимость | лимит токенов на evolve; урезанный max_iterations на eval; кэш прогонов champion; sonnet по умолчанию |
| Mutator ломает конфиги/промпты | pydantic-валидация, иммутабельные кандидаты, откат тривиален |
| Галлюцинации источников | URL только из web_search-результатов; метрика facts_with_valid_sources |
